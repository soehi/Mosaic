# Mosaic：整体架构思想

状态：已确认的架构原则。第一版已据此实施；实际验证范围见 [实施与验证记录](implementation-status.md)。

本文独立保存长期遵守的架构原则。具体技术、文件安排、开发步骤和测试见 [细节实现计划](implementation-plan.md)。

## 1. 目标

软件由职责清楚、能够独立替换的模块组成。宿主负责装配，模块负责自己的业务或技术能力。新增功能通过扩展公开契约、增加模块和修改装配配置完成，避免修改所有已有模块。

模块化首先是职责、接口、数据和依赖的约束。模块可以在同一进程中运行，是否跨进程由运行需求决定。

## 2. 每项职责只有一个所有者

- 每个业务概念、业务规则、持久化操作和系统装配规则，都有明确归属。
- 同一规则只维护一个权威实现，其他模块请求该实现执行。
- 多个页面可以展示同一数据，但不分别维护互相独立的权威数据。
- 输入结构检查、业务判断和数据库完整性约束各负其责。例如公开请求入口检查必填参数、类型和格式，任务模块检查标题是否符合业务要求，数据库负责完整性约束。
- 以能独立解释、测试和替换的职责划分模块，不按每个函数拆分。

## 3. 跨模块只能提出公开调用申请

> 模块只处理自己拥有的职责。需要其他能力时，只能通过对方公开的调用协议提出请求，不能调用其内部功能、获取内部对象或直接操作其数据。

```text
任务界面提出创建请求
  → 任务公开入口接收请求
  → 任务业务检查规则
  → 通过仓储接口提出保存请求
  → 存储适配器调用数据库公开能力
  → 保存完成，逐层返回结果
```

禁止以下行为：

- 页面跳过任务模块直接保存任务。
- 任务模块执行 SQL 或取得数据库驱动对象。
- 提醒模块直接修改任务表。
- 导入其他模块未公开的文件、读取其内部状态、修改其缓存。
- 将全部模块实例放入全局对象，允许任意模块随意取用。

公开入口接收申请后，按该层职责检查调用资格、参数和状态，执行并返回结果或拒绝原因。申请是程序协议，不需要用户逐次手工批准。

同进程可以通过注入的接口方法发出请求；跨进程通过受控代理发出请求。两者遵守同一契约，不强制每次调用都经过网络、事件总线或一个万能调度器。

## 4. 模块公开什么

| 项目 | 含义 |
| --- | --- |
| 标识与版本 | 唯一模块 ID，以及公开能力的兼容版本 |
| 职责范围 | 拥有的规则和数据，以及交给其他模块的事项 |
| 需要的能力 | 启动或运行时需要通过申请使用的外部能力 |
| 提供的能力 | 可请求的操作及其输入、输出、错误 |
| 生命周期 | 初始化、激活、停止接收请求、资源释放 |
| 可选界面贡献 | 导航、页面或宿主明确支持的扩展点 |

内部实现默认不公开。不兼容的契约变更升级能力主版本，并评估受影响的调用者。

## 5. 宿主装配与最小接口

- 宿主选择实现、校验配置、建立依赖并注入接口。
- 内核管理通用依赖和生命周期，不承包任务等业务。
- 模块声明需要什么，宿主只提供这些依赖，不提供整个系统的服务容器。
- 调用者只获得范围受限的接口或代理，不获得提供者的实现实例。
- 宿主通过公开模块入口装配，同样不得访问内部文件或代替模块实现业务。

同进程的可见性限制和依赖检查属于开发边界，不等于恶意代码的安全沙箱。未来如果执行不可信第三方模块，需要另行设计进程隔离和权限机制。

## 6. 缺少能力时如何扩展

1. 检查是否已有拥有这项职责的模块。
2. 已有模块拥有该职责：为它补充公开能力，调用者通过申请使用。
3. 属于新的独立职责：创建模块，定义契约、数据所有权和依赖后接入宿主。
4. 不在调用者中复制别人的能力，不通过越界访问临时绕过接口。

例如，任务筛选通常扩展任务模块；提醒计划适合创建提醒模块，通过任务 API 获取需要的信息。

创建模块发生在开发阶段。运行时缺少必需能力时明确失败，不自动生成、下载或隐式启用模块。

## 7. 数据与存储的边界

- 业务模块拥有业务模型和规则。
- 存储接口表达业务需要的保存、读取和查询操作。
- 业务存储适配器拥有对应 SQL、数据映射和表结构迁移。
- 数据库基础设施拥有连接、事务执行、迁移执行和资源释放。
- 宿主在启动时配置数据库位置和连接策略，业务请求不携带 SQL、路径或驱动对象。

数据库基础设施通过公开会话协议向存储适配器提供查询和事务能力，驱动原始对象保留在内部。其他模块请求业务 API，不能自行查表。

替换存储实现时继续使用相同仓储契约。历史数据迁移、云端一致性和冲突处理仍需专门设计。

## 8. 界面由激活功能贡献参数

- 功能模块提供导航和页面描述；外壳只负责通用布局、导航渲染和页面容器。
- 没有功能列表参数，就不显示业务功能导航。
- 依赖满足且激活成功后才能注册入口。
- 导航必须关联已注册页面；重复标识、缺失页面拒绝注册。
- 关闭界面模块后，导航、页面和快捷入口一起移除。
- 关闭后端能力后，相关调用入口不可用；隐藏菜单不等于禁用能力。
- 关闭模块不删除它已经保存的数据。

外壳不维护业务菜单副本，也不通过业务功能名分支决定显示内容。

## 9. 请求、结果和事件

- 查询读取数据，命令申请改变状态，都有明确的结果和错误。
- 写入提交成功后才能宣告保存成功，拒绝和失败不能被包装成成功。
- 事件表示已经发生的事实，不能代替需要确认结果的保存请求。
- 非幂等写入不自动重试；如需重试，先定义重复请求处理规则。
- 版本、取消、超时或幂等需求写进对应契约，不让调用者猜测。

第一版采用请求与返回结果，不提前建立通用事件总线。

## 10. 可验证的依赖与生命周期

- 启动前检查缺失依赖、循环依赖、版本冲突和重复能力提供者。
- 必需依赖缺失时明确失败，不静默替换为其他存储或模拟实现。
- 按依赖顺序启动，按相反顺序释放资源。
- 激活失败时回收已启动资源并撤销入口，避免半启用状态。
- 关闭前停止接受新请求，并处理在途操作。
- 配置描述期望启用状态；实际能力列表描述成功激活状态，两者不能混用。

## 11. 用工具维持边界

必须具备以下实施检查：

1. 公开入口白名单，通过语言可见性和构建边界限制可以访问的内容。
2. 引用与依赖检查，阻止内部实现访问、未声明依赖和禁止的框架依赖。
3. 请求入口检查，根据已激活能力与允许操作处理调用。
4. 契约测试，更换适配器后仍满足同一业务接口。
5. 禁用测试，检查导航、页面和调用入口与相应能力状态一致。

新增功能评审必须回答：职责属于谁、数据属于谁、通过什么接口协作、缺少依赖时如何表现、如何验证没有越界。

## 12. 变更规则

本文件保存架构决策，实现计划不得悄悄放宽这些约束。需要调整原则时，先记录原因、受影响模块和替代方案，再更新本文件及实施计划。

## 13. 同步交付规则

一次需求变更必须作为同一个交付单元完成：源码、测试、用户可见行为、发布说明和实施记录一起提交，不允许"先改一部分，其余以后再补"。凡改动会影响旧数据目录、配置文件、安装升级或模块装配的项目，必须同时交付对应的配置迁移逻辑和迁移验收项；只更新产物而不更新已有数据目录配置视为交付不完整。发布说明必须写清本次变更对已有安装的影响（例如旧配置是否会自动迁移、需要用户手动做什么）。

每次修复还必须在交付说明中给出两处定位，并同时写入实施记录或发布说明：

- 根因位置：具体到文件与行号，或类型与方法，说明触发条件以及为什么会在那里出错；不得只描述现象。
- 改动位置：列出每个被修改的文件及其中对应的类型、方法或行号；新增文件同样列出。

禁止只写"已修复"而不给位置。定位信息用于复查、回归测试和后续同步，属于交付物的一部分。

后续新增“更新简要”任务能力时，每次发布的用户可见全部功能变化必须从同一发布内容源生成发布说明与包内清单。生成更新任务只能向 Tasks 公开幂等创建能力提出申请；任务与创建回执由任务存储适配器原子保存，不在宿主配置里另存一份成功标记。具体行为与待实施状态见 [任务速览 UI 与更新简要任务计划](peek-and-update-summary-plan.md)。

## 悬浮内容扩展约定（0.8.0）

通用窗口模块比较不透明 ProviderId/ItemKey，拥有窗口状态和独立恢复表，不取得任务 DTO。Tasks UI 提供内容工厂和可撤销的分离申请来源，窗口模块在激活后注册处理器，故依赖单向且无循环。任务完成状态仍申请 Tasks API；Tasks Core 只在提交成功后发布专用变更事实。布局与任务写入分别排空，真正退出保留窗口恢复资格，用户单独关闭则先保存 IsOpen=false。
